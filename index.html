01 — La solución

Del papel a la plataforma

Antes · el problema

Formatos en Excel y Word, enviados por correo, con seguimiento manual. El estudiante no ve el estado de su trámite y las reuniones se coordinan por WhatsApp.

Ahora · SIVU

Los 5 formatos se diligencian dentro de la plataforma y se generan como PDF oficial. Notificaciones automáticas, expediente digital y agendamiento colaborativo.

Qué hace cada actor (según sus permisos reales)

🎓 Estudiante

Crea y firma el Plan, redacta y entrega el Informe Final, propone reuniones y pide revisión con IA.

🧑‍🏫 Docente Acompañante

Crea, edita y firma las Actas, publica su disponibilidad y responde reuniones, comenta y firma el Plan.

🏢 Tutor Empresarial

Diligencia y firma la Evaluación del Tutor, califica el Informe, participa y firma el Plan, ve sus actas/reuniones. (Cuenta o token externo.)

🗂️ Oficina de Coformación

Asigna la práctica, registra la Evaluación del Docente, aprueba/rechaza el Informe y consolida las notas.

Además de estos 4 actores del proceso, el rol 👑 Admin administra los usuarios del sistema y asigna roles.

03 — Arquitectura global

Una petición, paso a paso

Ejemplo real: el estudiante envía su Plan de Actividades (GAC-FM-10).

1

El estudiante llena el formulario Front

React valida los datos y envía la petición al backend con el token de sesión.

2

El backend autoriza y guarda Back

Valida el token JWT, comprueba el rol con @PreAuthorize y aplica las reglas; persiste en PostgreSQL.

3

Los datos quedan relacionados BD

El plan y sus objetivos y meses cuelgan del trimestre del convenio (integridad por llaves foráneas).

4

Notifica y, al firmar los 3, genera el PDF Back

Avisa a docente y tutor. Cuando los tres firman, OpenPDF genera el PDF oficial y lo guarda en el expediente.

5

El estudiante ve el estado al instante Front

TanStack Query refresca el expediente con el nuevo estado y el PDF descargable.

04 — Persistencia poliglota

Dos motores, dos paradigmas

El enunciado exige PostgreSQL para el core y otra tecnología para los usuarios. Usamos los dos modelos que existen: uno relacional y uno no relacional.

🔶 PostgreSQL · RELACIONAL
  • Tablas con filas y columnas, unidas por llaves foráneas y consultadas con JOINs.
  • Guarda el dominio académico: convenios, cortes, los 5 documentos, notas, agendamiento.
  • Elegido porque el proceso tiene muchas relaciones e integridad estricta (un plan pertenece a un corte, que pertenece a un convenio…).
🍃 MongoDB · NO RELACIONAL
  • Documentos JSON anidados, sin tablas ni JOINs; cada usuario es un documento autocontenido.
  • Guarda solo usuarios y autenticación: email, contraseña, roles.
  • Elegido porque es un agregado simple, de lectura rápida por email y esquema flexible.

04 — El modelo de datos

Los usuarios: un documento, no una tabla

En Mongo no hay tablas ni JOINs: cada usuario es un documento con sus campos anidados. Los enlaces al dominio (Postgres) son simples referencias por id.

usuarios · MongoDB Atlas · db=sivu_users
// un usuario = un documento autocontenido
{
  "email": "cmendoza@uempresarial.edu.co",
  "passwordHash": "$2a$10$…",        // BCrypt
  "roles": ["DOCENTE"],              // arreglo embebido
  "estudianteId": null,
  "empresaId": null,
  "tutorId": 1                       // referencia lógica al tutor en Postgres
}
Sin esquema rígido

Cada documento lleva solo los campos que necesita (un estudiante trae estudianteId, un tutor trae tutorId).

Lectura directa

El login busca por email y trae todo el usuario en una sola lectura, sin unir tablas.

Roles como arreglo

ADMIN·COORDINADOR·ESTUDIANTE·DOCENTE·TUTOR·MCP_AGENT viven embebidos en el propio documento.

05 — Despliegue continuo · cómo lo usamos

Nuestro flujo: del commit a producción, solo

Trabajamos en ramas. La CI valida cada Pull Request y, al mergear a master, la CD despliega sola — nadie sube nada a mano.

1 · Rama
feature/…
2 · Pull Request
CI corre 5 jobs y los valida
3 · Merge a master
solo si CI en verde
4 · CD despliega
Render + Vercel · automático
5 · Producción
en vivo
.github/workflows/ci.yml
on:
  push:         { branches: [ master ] }   # merge a master → CI + CD (despliega)
  pull_request: { branches: [ master ] }   # cada PR → solo CI (valida, NO despliega)
concurrency: { cancel-in-progress: true }  # si subes otro commit, cancela el run viejo
La compuerta — el corazón del CD

El deploy tiene needs: [backend, frontend, mcp, api-contract, e2e]. Si un solo job falla, no despliega: producción nunca recibe código roto.

Dos disparadores

PR → solo CI (build + pruebas). Push a master → CI + Docker→GHCR + CD (Render + Vercel).

05 — Despliegue continuo · backend

CI/CD del backend, a fondo

1

Build + test carpeta backend/

Levanta Postgres 16 + Mongo 7 reales y corre mvn clean verify: compila y ejecuta las 21 pruebas JUnit (Jwt · Auth · Estudiante · Evaluación) + cobertura JaCoCo.

2

Calidad + contrato

mvn sonar:sonar → SonarCloud. En paralelo, Newman corre la colección Postman (login, 401, CRUD, 422…) contra el backend levantado.

3

Empaqueta en Docker → GHCR

build-push-action con context ./backend (Dockerfile multi-stage) publica ghcr.io/jaydethsp01/sivu/backend.

4

Despliega a Render

La CD llama la Deploy API de Render por curl → redespliega el backend y el IA sidecar.

ci.yml · backend + deploy
backend:
  services: { postgres:16, mongo:7 }        # BD reales para los tests de integración
  steps:
    - working-directory: backend
      run: mvn -B clean verify             # compila + 21 JUnit + JaCoCo
    - working-directory: backend
      run: mvn sonar:sonar                 # SonarCloud

deploy:                                     # solo en master, tras la compuerta
  run: curl -X POST …/services/$RENDER_BACKEND_ID/deploys   # backend → Render
  run: curl -X POST …/services/$RENDER_SIDECAR_ID/deploys   # IA sidecar → Render

06 — Despliegue continuo · frontend

CI/CD del frontend, a fondo

1

Build carpeta frontend/

npm install --legacy-peer-deps + npm run build → tsc chequea los tipos y Vite genera el dist/. Falla si hay un error de tipos.

2

E2E contra el stack REAL Cypress

El job levanta el jar del backend (java -jar) y sirve el dist; luego cypress run valida 3 flujos de verdad: 01-auth, 02-estudiantes, 03-coformacion.

3

Empaqueta en Docker → GHCR

build-push-action con context ./frontend publica ghcr.io/jaydethsp01/sivu/frontend.

4

Despliega a Vercel

Construye con VITE_API_BASE_URL al backend de Render, hace vercel deploy --prod y fija el alias sivu-platform.vercel.app.

ci.yml · frontend + e2e + deploy
frontend:
  working-directory: frontend
  run: npm install --legacy-peer-deps  &&  npm run build   # tsc + Vite → dist/

e2e:                                        # prueba contra el stack real
  run: java -jar backend/target/sivu-backend.jar &   # levanta el backend
  working-directory: tests/cypress
  run: npx cypress run --browser chrome

deploy:  working-directory: frontend          # solo en master
  env: { VITE_API_BASE_URL: https://sivu-backend.onrender.com/api/v1 }
  run: npx vercel deploy dist --prod  &&  vercel alias set … sivu-platform.vercel.app

Calidad

Las pruebas que corren en cada push

Cinco tipos de prueba se ejecutan en el pipeline. Si una sola falla, la compuerta no despliega.

🔵 Backend · Jaydeth
  • JUnit — 21 unitarias (mín. 6): JwtServiceTest (genera/valida el token), AuthServiceTest (login·refresh·registro·401), EstudianteServiceTest (CRUD + email/documento duplicado), EvaluacionServiceTest (reglas de nota).
  • JaCoCo — mide la cobertura del código; el reporte se sube como artefacto.
  • Newman — corre la colección Postman contra el backend real: login por rol, 401 inválido, CRUD estudiantes (201/204), 422 duplicado, convenios y Coformación v2.
  • SonarCloud — bugs, code smells y duplicación (quality gate).
🟢 Frontend · Bryam
  • tsc — chequeo de tipos en el build; falla si hay un error de tipo.
  • Cypress E2E — en Chrome, contra el stack real (levanta el jar del backend y sirve el dist):
  • 01-auth — login, rechaza credenciales (401), ruta protegida redirige a /login.
  • 02-estudiantes — lista con el seed (Kelly), crea (201), obtiene, elimina (204).
  • 03-coformacion — crea la práctica, consulta el expediente y las disponibilidades.
k6 · rendimiento — equipo

Simula carga concurrente de login y mide latencia y tasa de error del backend.
